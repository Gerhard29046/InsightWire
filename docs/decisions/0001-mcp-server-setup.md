# ADR 0001: MCP Server Setup (Phase 1)

**Status:** Accepted
**Date:** 2026-08-07

## Context

The project requires a broad set of MCP (Model Context Protocol) servers to support development: filesystem access, git/GitHub operations, database access, cloud provider integration (Cloudflare, Supabase), browser automation, AI model access, memory/knowledge graph, and search.

Installing everything at once was rejected in favor of a phased rollout, gated on whether a server needs external credentials:

1. **Phase 1 (this ADR):** core dev servers needing no credentials.
2. **Phase 2:** GitHub, Docker (needs credentials/local daemon — parked until ready).
3. **Phase 3+:** Cloudflare, Supabase, memory/knowledge-graph, browser automation, search, multi-model orchestration.

## Decisions

### Installed (Phase 1 — no credentials required)

| Server | Package | Runtime | Notes |
|---|---|---|---|
| Filesystem | `@modelcontextprotocol/server-filesystem` | npx (Node) | Scoped to this project directory |
| Sequential Thinking | `@modelcontextprotocol/server-sequential-thinking` | npx (Node) | |
| Git | `mcp-server-git` | pip (Python) | Local git operations |
| Fetch | `mcp-server-fetch` | pip (Python) | Web fetching |

**Known issue:** `mcp-server-fetch` 2026.7.10 is incompatible with `mcp` SDK 2.0.0 (the SDK renamed `McpError` → `MCPError`, which `mcp-server-fetch` doesn't yet import). Fixed by pinning the global pip environment to `mcp==1.29.0`. This is a **global pip pin** — any future Python MCP server requiring `mcp>=2.0` will conflict and need its own virtualenv rather than a further global downgrade/upgrade.

### Installed (Phase 2, partial)

| Server | Package | Auth | Notes |
|---|---|---|---|
| GitHub | `@modelcontextprotocol/server-github` | Reused existing `gh` CLI OAuth token (`gh auth token`) rather than requesting a new PAT | Repo: [Gerhard29046/InsightWire](https://github.com/Gerhard29046/InsightWire) |

### Explicitly skipped / deferred

- **Terminal MCP** — redundant; Claude Code's harness already provides Bash/PowerShell execution.
- **Docker MCP** — Docker is not installed on this machine. User will install Docker Desktop independently; server will be registered once the daemon is available.
- **Cloudflare (Workers/Pages/R2/AI Gateway)** — deliberately deferred until the user is ready to connect it, to avoid MCP tooling auto-provisioning a Worker. **Decision: when connected, default target is Cloudflare Pages, not a Worker**, per explicit user preference.
- **Supabase** — project identified (`https://loelneyenvxcuyoluksd.supabase.co`) but not yet connected; requires a Supabase access token to be generated by the user first.

### Flagged, not acted on

- The user's global `~/.claude/CLAUDE.md` contains an auto-generated "Ruflo Integration" block referencing MCP tools (`memory_store`, `swarm_init`, `agent_spawn`, etc.) that are **not** currently registered in any MCP config (`claude mcp list` shows nothing named `ruflo`). User confirmed the setup was intentional; the underlying repository/tool still needs to be identified before a working `ruflo` MCP server can be registered. Tracked as a Phase 3 follow-up (memory/orchestration).

## Consequences

- Local dev environment now has working filesystem, git, fetch, sequential-thinking, and GitHub MCP servers.
- Global pip environment is pinned to `mcp==1.29.0`; revisit if a future Python MCP server needs the 2.x SDK.
- No cloud provider (Cloudflare, Supabase) is connected yet — nothing can be deployed or provisioned through MCP tooling until those phases are explicitly greenlit.
